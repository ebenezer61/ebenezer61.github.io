The expression is not enough

One program written twice, and four chapters where the answer depends on what the page does not show — gemma-2-2b passes 1 of 13 pairs

Companion to the attribution-graph study and Right name, wrong rules

  • The main experiment
  • The ten binding traps

In one paragraph

The main experiment shows gemma-2-2b tracking what a name is bound to; the trap pairs show it does not hold the rules of when a binding happens. This page pushes on two more fronts, with 35 scored single-token cases across two probes, 30 of them new. First, PEP 289 defines a generator expression to mean its desugared generator function — one program, written twice — and the model is worse on the form a human would actually write, on both cuts probed. Second, four chapters of behaviours where the printed expression underdetermines the answer (float width, hash-table order, bound-method identity, interpreter version): 1 of 13 pairs pass. The model answers float comparisons by literal identity rather than arithmetic, assumes sets preserve insertion order at 97.3% confidence, and gives the same locals() answer for Python 3.11, 3.12 and 3.13 — versions across which the answer changed.

The design, and three new honesty mechanisms

Everything from the trap probe's design carries over: ground truth is executed, not remembered — here under the exact interpreter (python3.11/3.12/3.13 where a case names one) and environment (PYTHONHASHSEED=0 where it matters) — every case cuts at a single-token divergence point, and cases come in pairs of near-identical form with opposite answers. Three new mechanisms were each forced by a failure observed while building this probe:

  • Coverage, because the model may not be answering. On bare >>> expr prompts the model's top prediction was >>> itself, at 37–45% — it declined to answer and moved to the next prompt, leaving both candidates in the noise. The summary now prints P(correct) + P(wrong) for every case, so a verdict resting on scraps is visible as such.
  • Counterbalanced priming, because the context can answer for the model. The fix for the non-answering failure is two worked True/False exchanges before the prompt — but a primer can bias the answer, so every primed case runs under both primer orders, and a verdict that flips with the order scores prime-dep, not a win. Three cases flipped, including 0.1 + 0.2 == 0.3 itself: an exact 48.83/48.83 split under one primer, 74.2% True under the other. That verdict belongs to the primer.
  • Exact ties score tie, because argmax invents a preference. bfloat16 makes exact ties common (40.43/40.43, 44.14/44.14 in this work). Argmax resolves them by candidate order — and the correct candidate is always listed first, so every such coin flip would have been recorded as a hit.

One program, written twice (PEP 289)

The material is real — snippets from a teaching video, kept precisely because synthetic prompts invite "you designed that": 

>>> lst = [1, 2, 3, 4, 5]
>>> g = (n for n in lst if n in lst)
>>> lst = [0, 1, 2]
>>> print(list(g))
[1, 2]

The iterable is captured eagerly (old [1..5]); the filter resolves the global lazily (new [0,1,2]); the output is their intersection — neither list on the page. PEP 289 defines this expression to mean its desugaring: an explicit generator function taking iter(lst) as an argument and filtering on the global. That desugared form is the second spelling the probe uses: 

>>> lst = [1, 2, 3, 4, 5]
>>> def __g(it):
...     for n in it:
...         if n in lst:
...             yield n
...
>>> g = __g(iter(lst))
>>> lst = [0, 1, 2]
>>> print(list(g))
[1, 2]

The probe cuts both spellings at the same two points. A disagreement between them rules out reading of the semantics outright; agreement proves little, since two matching wrong answers also agree.

Cut (correct token)Genexp formDesugared form
which list is iterated (1) 0 at 55.08% vs 1 37.70% — MISS 40.43% / 40.43% — exact tie
which list the filter uses (]) 53.12% — ok, margin 6.25 pp 73.05% — ok, margin 46.09 pp

Both cuts move the same way: the sugar itself costs it. Controls rule out the cheap explanations — with no reassignment it is correct at 99.61% at the same list length, so closing the list early is not a taste for short lists; merely adding the vacuous filter if n in lst, before any rebinding, costs 10 pp (89.45%). On the one cut that cleanly separates eager from lazy capture (whether (3, …) appears after the inner list is exhausted), the correct continuation receives 0.00%.

Stated carefully: this supports surface-form reading over semantics, it does not establish it. The design catches an outright contradiction between the two spellings, and it did not get one — an exact tie has no answer to contradict.

Four chapters, thirteen pairs, one pass

Twenty-six scored cases in four separately scored chapters — separately, because pooled accuracy across a float-arithmetic chapter and an interpreter-versioning chapter measures nothing. The single passing pair is list-vs-set order preservation, the least surprising in the set.

ch.1 — floats: literal identity, not arithmetic (0/6 pairs)

1e500 is not a big number — the literal overflows to inf at parse time, and 1e500/1e500 is nan. Twelve cases, six pairs, and all twelve verdicts fit a single heuristic: same expression written twice → True, different literals → False.

Each prompt is >>> expr preceded by two worked exchanges (>>> 1 == 2 → False, >>> 1 == 1 → True), run in both orders; the model column shows the answer under each order.

ch.3 — bound methods: CPython behaviour, stated as such (0/3 pairs)

o.f constructs a fresh bound method on every attribute access, so o.f is o.f is False while C.f is C.f and o.f == o.f are True — and id(o.f) == id(o.f) is True only because the allocator hands the freed address straight back, which a single interleaved allocation flips to False (both stable 5/5 on this build). This chapter is marked implementation-defined in the harness: a ground-truth mismatch on another build warns instead of aborting, and none of it is evidence about "Python".

What this bounds

With the trap pairs, the picture is consistent across three probes and 45 scored cases: the mechanism the main experiment verified tracks which name carries how much drive, and essentially nothing beyond it. When the answer requires evaluation — of time, of scope, of float width, of a hash table, of an interpreter version — the model substitutes the nearest surface regularity, often at high confidence. For an AI debugging tool this is the exact failure profile that matters: the places where the expression on the page underdetermines the behaviour are the places debugging happens.

One model, behavioural probes only, single-token cuts; no cross-model claims.

Reproducing this

Both probes are plain transformers forward passes on google/gemma-2-2b in bfloat16 — no transcoders, no attribution run. The scripts (probe_late_binding.py, probe_gotchas.py, in the same currently-private fork as the main experiment's code) execute every snippet before loading the model — under the interpreter and environment each case names — and refuse to start unless the prompt is a true prefix of what Python prints, the candidate labelled correct is the actual next character, and the distractor is not. The complete per-token outputs behind every number on this page: probe_late_binding_gemma-2-2b.txt and probe_gotchas_gemma-2-2b.txt.
