The expression is not enough

One program written twice, and four chapters where the answer depends on what the page does not show. gemma-2-2b passes 1 of 13 pairs

Companion to the attribution-graph study and Right name, wrong rules

  • The main experiment
  • The ten binding traps

In one paragraph

The main experiment shows gemma-2-2b tracking what a name is bound to. The trap pairs show it does not hold the rules of when a binding happens. This page pushes on two more fronts, with 35 scored single-token cases across two probes, 30 of them new. First, PEP 289 defines a generator expression to mean its desugared generator function: one program, written twice. The model is worse on the form a human would actually write, on both cuts probed. Second, four chapters of behaviours where the printed expression underdetermines the answer (float width, hash-table order, bound-method identity, interpreter version): 1 of 13 pairs pass. The model answers float comparisons by literal identity rather than arithmetic. It assumes sets preserve insertion order at 97.3% confidence. It gives the same locals() answer for Python 3.11, 3.12 and 3.13, versions across which the answer changed.

The design, and three new honesty mechanisms

Everything from the trap probe's design carries over. Ground truth is executed, not remembered, here under the exact interpreter (python3.11/3.12/3.13 where a case names one) and environment (PYTHONHASHSEED=0 where it matters). Every case cuts at a single-token divergence point. Cases come in pairs of near-identical form with opposite answers. Three new mechanisms were each forced by a failure observed while building this probe:

  • Coverage, because the model may not be answering. On bare >>> expr prompts the model's top prediction was >>> itself, at 37–45%. It declined to answer and moved to the next prompt, leaving both candidates in the noise. The summary now prints P(correct) + P(wrong) for every case, so a verdict resting on scraps is visible as such.
  • Counterbalanced priming, because the context can answer for the model. The fix for the non-answering failure is two worked True/False exchanges before the prompt. But a primer can bias the answer, so every primed case runs under both primer orders. A verdict that flips with the order scores prime-dep, not a win. Three cases flipped, including 0.1 + 0.2 == 0.3 itself: an exact 48.83/48.83 split under one primer, 74.2% True under the other. That verdict belongs to the primer.
  • Exact ties score tie, because argmax invents a preference. bfloat16 makes exact ties common (40.43/40.43, 44.14/44.14 in this work). Argmax resolves them by candidate order. The correct candidate is always listed first, so every such coin flip would have been recorded as a hit.

How a case is scored

One forward pass per prompt. From the softmax at the cut the probe reads two numbers: P(correct) and P(wrong), the probability of the correct continuation and of the natural misreading. It ignores every other token. From those two numbers:

  • coverage = P(correct) + P(wrong). How much of the model's answer the two candidates account for. It is printed for every case. It is not a verdict, but it says how much the verdict is worth. At 97% the model chose between the two tokens. At 19% (dict-reversed-keeps-order) it mostly predicted something else, and the verdict rests on scraps.
  • margin = |P(correct) − P(wrong)|. Reported, not thresholded: no cutoff below which a win stops counting is claimed.
  • noise: the larger of the two candidates is below 2%. The answer is neither token; the case scores nothing.
  • tie: margin is exactly 0. The two candidates have identical probability, which in bfloat16 happens often. Scored as neither ok nor MISS, and it fails its pair.
  • ok: P(correct) > P(wrong), by any margin.
  • MISS: P(wrong) > P(correct).
  • prime-dep: ch.1 only, where each case runs under two primer orders. If the two runs give different verdicts, the case is prime-dep regardless of what they were; only two matching verdicts carry through. The two primers are shown at the top of ch.1.

How a pair is scored

Same rule as the trap probe: a pair passes only if both members are ok. A tie, noise or prime-dep on either side fails it just as a MISS does. Pairs are counted per chapter and never pooled across chapters, because ch.1 is float arithmetic and ch.4 is a fact about interpreter releases. One number over both measures nothing. Cases marked unscored (the unseeded string set, whose output changes with the process) are executed and shown but never put to the model. The seeded string set is scored but unpaired.

One program, written twice (PEP 289)

The material is real. The snippets come from a teaching video, kept precisely because synthetic prompts invite "you designed that": 

>>> lst = [1, 2, 3, 4, 5]
>>> g = (n for n in lst if n in lst)
>>> lst = [0, 1, 2]
>>> print(list(g))
[1, 2]

The iterable is captured eagerly (old [1..5]). The filter resolves the global lazily (new [0,1,2]). The output is their intersection, neither list on the page. PEP 289 defines this expression to mean its desugaring: an explicit generator function taking iter(lst) as an argument and filtering on the global. That desugared form is the second spelling the probe uses: 

>>> lst = [1, 2, 3, 4, 5]
>>> def __g(it):
...     for n in it:
...         if n in lst:
...             yield n
...
>>> g = __g(iter(lst))
>>> lst = [0, 1, 2]
>>> print(list(g))
[1, 2]

The probe cuts both spellings at the same two points. A disagreement between them rules out reading of the semantics outright; agreement proves little, since two matching wrong answers also agree.

Cut (correct token)Genexp formDesugared form
which list is iterated (1) 0 at 55.08% vs 1 37.70% (MISS) 40.43% / 40.43% (exact tie)
which list the filter uses (]) 53.12% (ok, margin 6.25 pp) 73.05% (ok, margin 46.09 pp)

Both cuts move the same way: the sugar itself costs it. Controls rule out the cheap explanations. With no reassignment it is correct at 99.61% at the same list length, so closing the list early is not a taste for short lists. Merely adding the vacuous filter if n in lst, before any rebinding, costs 10 pp (89.45%). On the one cut that cleanly separates eager from lazy capture (whether (3, …) appears after the inner list is exhausted), the correct continuation receives 0.00%.

Stated carefully: this supports surface-form reading over semantics, it does not establish it. The design catches an outright contradiction between the two spellings, and it did not get one. An exact tie has no answer to contradict.

Four chapters, thirteen pairs, one pass

Twenty-six scored cases in four separately scored chapters. Separately, because pooled accuracy across a float-arithmetic chapter and an interpreter-versioning chapter measures nothing. The single passing pair is list-vs-set order preservation, the least surprising in the set.

ch.1, floats: literal identity, not arithmetic (0/6 pairs)

1e500 is not a big number. The literal overflows to inf at parse time, and 1e500/1e500 is nan. Twelve cases, six pairs, and all twelve verdicts fit a single heuristic: same expression written twice → True, different literals → False.

Every prompt in this chapter is one bare expression. On its own the model tends to answer with another >>> rather than a value, so two worked exchanges are placed in front of it. Because the last exchange might bias the answer, each case is run twice, once under each order. False-first and True-first are the names of those two prompts. A case only counts if both runs agree:

False-first: the False exchange comes first

>>> 1 == 2
False
>>> 1 == 1
True
>>> <expr>
█

True-first: the same two exchanges, swapped

>>> 1 == 1
True
>>> 1 == 2
False
>>> <expr>
█

Each block below reports the answer under both. prime-dep means the two runs gave different verdicts, so the verdict belongs to the primer, not the model.

The four identity-shaped cases (1e500 == 1e500, 1e500/1e500 == 1e500/1e500, 1e50 == 1e60, 1e500 == 1e600) are the tell. The verdict tracks whether the two sides are the same string, never what they evaluate to. Nothing was computed. The three prime-dep cases are exact ties under one primer and a confident answer under the other, so the verdict belongs to the primer. The exact/inexact pairs were answered True both ways, consistent with a general lean toward True on arithmetic that is not an identity comparison.

ch.2, sets: the order you see is the hash table (1/3 pairs)

dicts preserve insertion order; sets never promised to. The sharpest minimal pairs in the whole probe: a dict comprehension and a set built from the same elements, both printed with braces, opposite first element.

Pairs: dict-reversed/set-reversed fails on the dict side, where the model mostly predicted neither candidate. dict-int/set-int fails too. The wrap case is the most confident wrong answer in this study: the model assumes sets keep insertion order the way dicts do. list-reversed/set-reversed is the one pass. The string-set case under PYTHONHASHSEED=0 is included only as a floor: deterministic but underivable, since passing it would mean having memorised CPython's siphash. The unseeded variant is executed under two seeds to prove its output differs, then never shown to the model. There is no correct token to score.

ch.3, bound methods: CPython behaviour, stated as such (0/3 pairs)

o.f constructs a fresh bound method on every attribute access, so o.f is o.f is False while C.f is C.f and o.f == o.f are True. id(o.f) == id(o.f) is True only because the allocator hands the freed address straight back. A single interleaved allocation flips it to False (both stable 5/5 on this build). This chapter is marked implementation-defined in the harness. A ground-truth mismatch on another build warns instead of aborting, and none of it is evidence about "Python".

What this bounds

With the trap pairs, the picture is consistent across three probes and 45 scored cases. The mechanism the main experiment verified tracks which name carries how much drive, and essentially nothing beyond it. When the answer requires evaluation (of time, of scope, of float width, of a hash table, of an interpreter version), the model substitutes the nearest surface regularity, often at high confidence. For an AI debugging tool this is the exact failure profile that matters. The places where the expression on the page underdetermines the behaviour are the places debugging happens.

One model, behavioural probes only, single-token cuts; no cross-model claims.

Reproducing this

Both probes are plain transformers forward passes on google/gemma-2-2b in bfloat16: no transcoders, no attribution run. The scripts (probe_late_binding.py, probe_gotchas.py, in the same currently-private fork as the main experiment's code) execute every snippet before loading the model, under the interpreter and environment each case names. They refuse to start unless the prompt is a true prefix of what Python prints, the candidate labelled correct is the actual next character, and the distractor is not. The complete per-token outputs behind every number on this page: probe_late_binding_gemma-2-2b.txt and probe_gotchas_gemma-2-2b.txt.
