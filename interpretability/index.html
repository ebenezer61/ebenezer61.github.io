Which variable does the model return?

An attribution-graph study of gemma-2-2b completing a Python function

  • Interactive attribution graph
  • Graph JSON (4.5 MB)
  • Attribution report (JSON)
  • Companion: where the rules break
  • Companion: the expression is not enough

In one paragraph

Give gemma-2-2b a Python function that accumulates into a local variable and cut the prompt off right after return. The model predicts  result — the accumulator it bound four lines earlier — with 95.3% probability. Using circuit-tracer to build an attribution graph over that prediction, the answer turns out not to be a frequency prior over common variable names: a specific mid-layer feature fires on the result tokens, and a band of late-layer features on return adds to the same logit.

One graph cannot say whether that feature tracks the variable being bound or simply the name result; in this prompt they coincide. Control prompts that move the binding around separate the two, and the answer is the name. Each variable name has its own pathway, and the pathways are orthogonal. The nodes sitting on result drive the  result logit and essentially nothing else; the nodes sitting on a second name, ans, drive  ans and essentially nothing else. Binding does not switch a pathway on or off. It sets how much drive that name accumulates, and the model takes the winner at the logit layer.

Three things then hold this up. Across five graphs no pathway pushes the rival logit by more than 2.0 while pushing its own by 17 to 39. The effect is not about the word result: 18 accumulator names behave the same way over four prompt shapes, including runnable Python. And it is causal — scale the winning name's feature down and the probabilities cross over, so the model returns the other variable.

The task

The prompt is a complete, unambiguous function whose body binds one local variable. Everything the model needs to answer correctly is in scope; nothing about the surrounding text hints at the name. This is the first of four prompts, P1; the other three are controls (P2–P4) that move the binding around, and they are what the interpretation ultimately rests on.

P1 · return-variable. result is bound twice.

def calculate_total(prices):
    result = 0
    for price in prices:
        result = result + price
    return

That is 31 tokens including <bos>. The two writes to result land at positions 10 and 23; the final return is position 30, and that is where the next-token prediction is made.

Three things stand out.

One feature carries most of the positive effect, and it fires only on result. Feature 18_4769 is the single largest positive contributor, and it appears three times in the top nine — at both writes to result and at the newline that closes the first one. It never fires on price or prices. Two readings fit this one graph equally well: a feature for "the local variable being assigned here", or a feature for the name result. The controls decide between them — 18_4769 is tied to the name, and it stays silent through a perfectly good binding of a different name.

The raw embeddings contribute directly. E_10 and E_23, the plain token embeddings of the two result occurrences, contribute +2.56 and +2.20 without passing through any feature — a copy path straight from the input. In the controls this path carries a large share of each name's total, and it is name-specific in the same way the features are.

The largest single effect is negative. 24_15424_30 pushes the  result logit down by 5.09, almost exactly cancelling the top promoter. The prediction survives because the promoting evidence is distributed across many nodes, not because any one of them overwhelms the suppressor. The controls settle what this feature is: result's own dedicated suppressor. It fires against  result just as hard when  result is losing, and when the accumulator is a different name, a different layer-24 feature takes its place.

The controls

One prompt is not enough to interpret. In the function above, the name result and the variable that gets bound are the same thing, so a feature that fires on result could be tracking either. The controls below pull the two apart, and they come down on the side of the name.

Each control keeps the function, the loop and the cut point identical, and changes only which name is bound where. Two of them are deliberately invalid Python — a name is read before it is ever assigned — because making binding and mere occurrence disagree is the only way to tell which one the model follows. The third is ordinary runnable code, and it is the one to check first if the invalid ones bother you.

P2 · split-binding. ans is bound; result is accumulated into but never initialised. Invalid Python. 

def calculate_total(prices):
    ans = 0
    for price in prices:
        result = result + price
    return

P3 · result-never-bound. ans is bound twice; result only ever appears on a right-hand side. Invalid Python. 

def calculate_total(prices):
    ans = 0
    for price in prices:
        ans = result + price
    return

P4 · two-valid-locals. Both names are bound, and only result is accumulated into. This one runs. 

def calculate_total(prices):
    ans = 0
    result = 0
    for price in prices:
        result = result + price
    return

Binding clearly matters to the behaviour: move it and the answer moves with it, from 95.7% down to 6.5%. The question is how, and for that the graphs have to be read carefully.

Every number needs a named logit

A direct effect is meaningless until you say which logit it is measured against. The first prompt's graph has a single logit target, so there is nothing there to get wrong. The controls each carry several — both names clear the coverage threshold — and a node's effect on the top logit can be near zero while its effect on the other logit is large. Every number below names its target.

For each graph, take every node sitting on a name's tokens and sum its direct effect on each logit separately. P2, P3 and P4 each have two candidate names; two more graphs, split-total and total-never-bound, repeat P2 and P3 with total as the accumulator, to check that nothing here is about the word result:

Each variable name has its own pathway to its own logit, and the pathways are orthogonal. Binding does not switch a pathway on or off; it sets how much drive that name accumulates. The model then does a winner-take-all comparison at the logit layer.

What the graphs show

  • The features are tied to the name, not to the act of binding. 18_4769 does not respond to ans = 0 at all, and that is a perfectly good binding. A different feature, 18_4732, is the one that fires there.
  • A losing pathway is still fully routed. In P3, 18_4769 fires once (position 25, activation 92.5) and is worth +8.50 to  result; its largest firing in P2 (position 23, activation 91.0) is worth +8.94. Matched activation, matched effect, whether its name wins or loses. Likewise 18_4732 at activation 39.0 gives  ans +1.555 in one graph and +1.305 in the other: the same feature doing the same job. What changes between the graphs is how much total drive each name accumulates, not what any one feature does.
  • The ordering is consistent; the magnitude is not. The winning pathway's total runs 26.96 / 26.96 / 37.30 / 38.88 / 28.04 across the five graphs, a spread of 11.9. There is no fixed drive budget. What holds in every graph is that the winner's own-logit drive exceeds the loser's, and that the winner recruits more nodes (259 > 238, 500 > 102, 335 > 188, 560 > 183, 509 > 313) — a trend, not a mechanism.
  • Part of the drive is name-agnostic. 24_12518_30, on the return token, gives +1.680 to  result and +1.781 to  ans in P2 — a baseline "a local variable goes here" push that belongs to neither name's pathway.
  • Suppression is per-pathway, not global. 24_15424 presses on  result even where  result has already lost and sits at 6.5%, so it is not reacting to the outcome — and swapping the accumulator's name swaps the suppressing feature. Its own subsection, below.
  • Attribution and ablation agree, independently. Deleting 18_4732 from P3 moves  ans only 89.06% → 86.72% — small, and exactly what the graph predicts, because ans's drive sits mostly in its raw embeddings (+5.688 and +4.906) rather than in that feature (+1.305).

Each pathway has its own suppressor

The largest negative node in the first graph, 24_15424_30, could be a global calibrator that presses on whichever name is winning, or something specific to result. Swapping the accumulator for total answers that: each name's pathway is opposed by its own dedicated layer-24 feature at the return position. Rank the negative nodes into each pathway's own logit, as a fraction of that pathway's drive:

PathwaySuppressorMagnitude ÷ pathway drive, per graph
result 24_15424 0.285 / 0.263 / 0.240 / 0.292
total 24_12843 0.285 / 0.288

The load-bearing fact is qualitative, and it needs no ratio to state: change the accumulator from result to total and the suppressing feature index changes with it. Both are layer 24, both sit on return, but they are different features. One global calibrator would be the same feature in both.

The 0.24–0.29 band is an observation, not a law: six points across two names is not enough to call a ratio fixed, so it is reported and not leaned on. The claim rests on the feature indices, not on the ratio.

For ans the honest phrasing is "not captured", not "does not exist". Its drive sits in its raw embeddings (+7.375 in P4) rather than in its feature (+1.727) — the transcoders cover that pathway poorly, so its partner is presumably just not represented in the graph.

In P4 the pairing is at its most dramatic: 18_4769_16 drives  result at +10.562 while 24_15424_36 opposes it at −10.875 — the two largest-magnitude nodes anywhere in this project, very nearly cancelling.

A trap in reading the subgraphs

In P3 the pinned subgraph says the opposite of the outcome. The handful of pinned nodes give result +12.8 against ans +11.9 — and yet the model answers  ans at 89.1%. The true ordering appears only once every node at those positions is summed: +26.957 against +17.027. ans wins on breadth, not on peak: 500 nodes against 103.

So any subgraph figure has to carry the aggregate totals beside it, or a reader will draw the opposite conclusion from the picture. That is the general lesson rather than a quirk of this prompt: a pinned subgraph is a hypothesis about which nodes matter, and the aggregate is the check on it.

All four prompts' graphs are hosted on Neuronpedia with the relevant nodes pinned and every logit target pinned beside them. Each supernode label names the logit its total is measured against; the P2 and P3 labels give both the pinned total and the all-nodes aggregate, so the P3 subgraph cannot be read as saying result wins. The hosted copies are pruned harder than the graphs the table above is computed from, so their totals run somewhat lower.

P4 is the one to start with: it is the valid Python among them, it separates the two pathways most cleanly (the pinned pathway groups cross to the rival logit at just +0.29 and +0.24), and it holds the near-cancelling pair described above. In its pinned view the suppressor 24_15424_36 is deliberately left outside every group, so it reads as what it is — the single dominant opposer, not part of a distributed background. All three logit nodes are pinned, including ( at 1.3%: the two names are competing inside a real distribution, not a two-way choice we constructed.

Is any of this about the word result?

No. Sweeping 18 accumulator names through four prompt shapes, against the same distractor ans, the binding account predicts the top-1 token in 71 of 72 cases. total, buf, tally, subtotal, running and accum behave like result does.

ShapeRunnable?Top-1 correctMean margin
consistentyes18/18+94.8%
two-validyes18/18+59.6%
never-boundno, control18/18+89.0%
splitno, control17/18+26.5%

The one miss is reported as a miss. Under split, score lands on 44.92% against 44.92% — an exact tie in bfloat16, which the argmax breaks toward  ans. A tie is not a win, so it is counted as a miss.

Note also which shape is hardest. split has the smallest margins because it is the most conflicted prompt: one name is bound, a different one is accumulated into. That is the shape the pathway account predicts should be close, and it is.

This is also the answer to the obvious objection. Two of the control prompts are invalid Python, and a Python audience is right to be suspicious of conclusions drawn from code that cannot run. But two-valid is ordinary runnable code — both locals bound, one of them accumulated into — and it is 18/18 with a mean margin of +59.6%. The effect does not depend on the prompt being broken.

Turning one pathway down

Everything above is correlational: the attribution graph says which nodes are associated with which logit. The direct test is to intervene. Clamping feature 18_4769 — the result feature — to a fraction of its value at every position it fires, and re-running the forward pass, moves the answer smoothly and then flips it.

The response is monotonic in  ans throughout. The two candidates tie exactly at gain 0.4 and again at 0.3, and from 0.2 down  ans is ahead. Turning one name's volume down changes which variable the model returns — which is the claim, tested directly rather than inferred from the graph.

The baseline forward pass in this harness reproduces the probe exactly (95.31 / 69.14 / 6.45%), so the pipeline was verified before any of the intervention numbers were believed. Ablating outright, rather than scaling, does the same thing: removing 18_4769 from P2 takes  result from 69.14% to 24.02% and hands the argmax to  ans.

Why only scaling down counts

Amplifying a feature does not do the mirror image of ablating it. Scaling the losing ans feature up should, on a naive reading, raise  ans. It does not. Past about 6× it collapses: 27.2% at 6×, 7.7% at 16×, 2.6% at 32×, while  result climbs to 85.9%.

This is not a property of the pathway. It is the residual stream being pushed off the distribution the later layers were trained on, so the output falls back toward the prior. Scaling down stays inside the feature's natural range and is the intervention this page relies on; the amplification sweep is shown so the asymmetry is on record.

A mechanism this reliable invites a stronger reading than it has earned: that the model knows Python's binding rules. It does not. The pathways track which name carries how much drive, not when a name is resolved. Two companion pages probe that boundary with executed ground truth and paired prompts:

  • Right name, wrong rules — ten classic binding traps (closure capture, mutable defaults, loop-variable leak, class-body scope), posed as near-identical pairs with opposite answers: 0 of 4 pairs, with the two scoping rules exactly swapped in one pair.
  • The expression is not enough — PEP 289 generator-expression late binding, where the model is worse on the sugared form of the identical program, plus four chapters (float width, set order, bound-method identity, interpreter version) where the printed expression underdetermines the answer: 1 of 13 pairs.

A prompt design that does not work here

Cutting mid-identifier is not a usable probe on this model. A natural first design is to cut the prompt at return res and watch the model complete res → ult. That premise does not hold on gemma-2-2b, which is why the prompts above all cut at return instead.

Probed directly, the top prediction after  res is a newline (29.5%): the model accepts res as a complete variable name. And because  result and result are each a single token in Gemma's vocabulary, there is no high-probability res → ult BPE split to observe at all — the top identifier continuations are junk like ut and lut.

The attribution graph for that variant says the same thing from the inside: its strongest direct effects are transcoder error nodes at the  res position (E_23_31, E_19_31) — that is, behaviour the transcoders do not explain. High error-node attribution is a warning sign that the graph is not describing a clean circuit.

The practical lesson, and the reason it is on this page: probe the tokenizer and the top-k predictions before spending GPU time on attribution. A prompt design can be perfectly reasonable as Python and still be unanswerable as a next-token problem.

Three caveats. The page loads a 4.5 MB graph file and pulls its plotting libraries from transformer-circuits.pub and unpkg, so it needs a live connection and a moment to start.

The feature-detail panel on the right stays empty. It fetches example activations from Anthropic's own feature store, which hosts their scans and not GemmaScope, and there is no public equivalent to point it at — generating those examples means a GPU pass over a corpus, which is outside this experiment. Feature identifiers follow {layer}_{feature}_{position}; look a feature up on Neuronpedia to see what it responds to.

Finally, the node labels are mine, not the model's. GemmaScope transcoders ship without auto-interpretation text, so every feature node in the published graph is labelled with what is verifiable — its layer, feature index, the token it fires on and its activation — and nothing about what the feature means. The interpretive claims on this page come from the attribution numbers, not from the labels.

The graph hosted here is the first prompt's. On its own it shows the circuit but not what the circuit is tracking — that needs the controls. It does have one advantage: a single logit target, so a node's direct effect is unambiguous here in a way it is not in the controls. Read it alongside the Neuronpedia graphs for those.

Reproducing this

Everything below runs against the public safety-research/circuit-tracer release — no private code is needed to get the same graph. You will need a GPU with roughly 10 GB free in bfloat16 (18 GB in float32), and a Hugging Face account that has accepted the Gemma licence, since the first run downloads about 18 GB of weights and transcoders. 

git clone https://github.com/safety-research/circuit-tracer
cd circuit-tracer

uv venv .venv --python 3.11
uv pip install "torch==2.7.1" --index-url https://download.pytorch.org/whl/cu126
uv pip install .

.venv/bin/huggingface-cli login    # gemma-2-2b is a gated model

Then run the attribution:

.venv/bin/circuit-tracer attribute \
    -m google/gemma-2-2b \
    -t gemma \
    -p "$(printf 'def calculate_total(prices):\n    result = 0\n    for price in prices:\n        result = result + price\n    return')" \
    -o py-return-variable.pt \
    --dtype bfloat16 \
    --offload cpu \
    --batch_size 128 \
    --max_feature_nodes 8192 \
    --slug py-return-variable \
    --graph_file_dir graph_files \
    --node_threshold 0.8 \
    --edge_threshold 0.98 \
    --verbose

That writes graph_files/py-return-variable.json alongside the raw .pt graph. To view it locally, add --server to the command above, or serve an existing directory: 

.venv/bin/circuit-tracer start-server --graph_file_dir graph_files --port 8041

On thresholds. At the defaults (node 0.8, edge 0.98) the graph JSON is 76 MB, which is fine for the local viewer and unwieldy for anything else. The graph published on this page was re-pruned from the same saved .pt at node 0.7 / edge 0.9, giving 4.5 MB. Re-pruning does not require rerunning attribution, but it does still need the GPU.

Do not use float16. gemma-2's activation magnitudes overflow in fp16; use bfloat16 on Ampere or newer, and float32 on older cards. This is why the run above pins --dtype bfloat16 rather than letting a generic half-precision default apply.

The control prompts run through the same command; only -p and --slug change. Their per-logit numbers are read straight out of the graph JSON: for each node whose feature_type is logit, sum the links whose target is that node. Take every logit node, not just the first: on the first prompt there is only one, so reading the top logit alone happens to be correct there and silently wrong on the controls.

The 18-name sweep and the interventions need no transcoders and no attribution run — they are plain transformers forward passes, which is why they were used to check the graph rather than the other way round. The intervention harness clamps a feature through the transcoder at every position it fires and re-runs the model, reporting its unmodified baseline first so a broken hook cannot pass silently.

The scripts that produced the exact numbers on this page — the prompt probe, the name sweep, the intervention harness, the attribution driver, the per-position feature comparison and the re-pruning helper — live in a fork of circuit-tracer, circuit-tracer-python, which is currently private. The raw attribution reports behind the tables above are published here: py-return-variable_report.json, py-two-valid-locals_report.json, py-split-binding_report.json, py-result-never-bound_report.json.
